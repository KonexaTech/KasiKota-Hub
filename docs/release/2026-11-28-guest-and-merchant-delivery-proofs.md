# Disabled guest and merchant delivery proof controls

A guest cannot log in to Delivery using a Neon JWT. Kota now derives the proof role from separate existing customer/owner routes and authorizes the actual persisted customer or merchant before sending a server-only request. The request contains only version, source_order_id and purpose, signed with the distinct konexa-delivery-proof-v1 domain, pinned to the private Delivery origin with existing Access credentials and manual redirect rejection. Browser bearers, customer subjects, PIN values and payment amounts are never forwarded. Only explicitly labelled test delivery orders on an approved shop can use the staging path. Anonymous, other-customer, owner-as-customer and guest-as-owner calls are denied.

The existing customer tracker and owner orders dialog receive small conditional buttons. A code is displayed only for the current order, never stored or logged, and clears on order/account/visibility changes and expiry. Late responses after those changes are discarded. Lost issuance responses, already-issued or expired codes require the existing audited Delivery administrator recovery; no automatic insecure reissue.

Both controls and delivery checkout remain unavailable until KOTA_STAGING_DELIVERY_PROOFS_ENABLED and the existing safety prerequisites are enabled. The flag is not activated by this PR. Delivery companion PR40 must be reviewed/deployed and actual authenticated staging courier acceptance must pass before operational activation. No database migration, production change, new pricing policy, real payment or payout.
